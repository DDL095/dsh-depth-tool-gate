## 六、`explain_gate` 是什么

**一句话**：它是 dtg 的**只读诊断工具** —— 回答「我（这个 agent）现在看得见哪些工具、
看不见的那些是被哪条规则裁掉的」。

| 项 | 值 |
|---|---|
| 状态 | **只读**，不改任何状态（不写 config、不动 lock、不改工具面） |
| 调用方 | 派单失败诊断 / 子代理自检 / 面板口径对账 |
| 输入 | 无参数（自动取**调用者自己**的 agent 上下文） |
| 输出 | `{visibleCount, restrictableCount, deniedCount, denied:[{name, reason}]}`；**渲染为两层**（按归因分组的完整汇总 + 逐件明细，明细上限 200 且显式声明未展开数）—— v0.15.2 起 |
| 可见性 | **主会话可见；域会话可见**（v0.15.2 起已挪出 `baseline_deny`）。★ **v0.16.3 起组装子代也可见** —— `explain_gate` 已进**每一个**能力标签的 allow 名单（内建 5 组 + 生产 9 组逐个核过都含）⇒ 「缺工具先自查」铁律在组装面也能真正执行 |

**`reason` 的归因链**（按优先级，命中即止）—— 每一档都对应一个**可改的配置键**
⇒ 这张表本身就是「怎么修订」的指引：

| reason | 含义 | 修订动作（主会话在面板执行） |
|---|---|---|
| `preset_rules.deny(<preset>)(用户显式禁用)` | 用户在该 preset 的专属配置里显式禁的 | 改该 preset 的 `preset_rules.deny`（角色页「🎛 专属配置」） |
| `main_deny(主会话显式名单)` | 主会话全局禁用名单 | 改 `main_deny`（主会话按角色页） |
| `main_preset_extra_deny(<preset>)(主会话按角色禁用)` | 主会话按角色的额外禁用 | 改 `main_preset_extra_deny[preset]` |
| `baseline_deny(子代基线)` | 子代全局底线闸 | 改 `baseline_deny`；或对**某档 preset** 用 `preset_allow[preset]` 豁免（角色页勾「不禁用」自动写该表） |
| `preset_extra_deny(<preset>)` | 该 preset 的额外加裁 | 改 `preset_extra_deny[preset]`（角色页勾「禁用」自动写该表） |
| `preset_allow 正面清单外(<preset>)` | 不在该 preset 的正面清单里 | 把该件加进 `preset_allow[preset]`；若本意是宽松，改用 `preset_extra_deny` 表达 |
| `lock pending(新工具待裁决)` | 自动发现的新工具，等你裁决 | 面板裁决（决定 seen / 禁用 / 强制） |
| `lock preset 自带工具(<preset>)(不在本会话的挂载范围)` | 该工具由**别的** preset 声明，本会话没挂载 | 换用声明它的 preset / 挂载它；不是「被禁」而是「没挂」 |
| `dtg-unknown` | 以上都没命中（= 报告缺失，视为缺陷信号） | **报缺陷** ⇒ 每条档位都是这条链的分支，出现它说明归因链漏了一条通道 |

★ `explain_gate` **只读**（不写 config / 不动 lock / 不改任何 agent 的工具面）
⇒ 修订一律由**主会话**在面板执行；域子代的职责是「查清并如实报告归因」。

**为什么要它**：工具面治理最怕「工具不见了但说不出为什么」。`explain_gate` 把
「被裁 + 为什么裁」一起给出 ⇒ 派单失败时能立刻定位是哪条规则、哪个 preset。

## 七、把 `explain_gate` 挪出 `baseline_deny` —— **v0.15.2 已实施**

**原状态**：`explain_gate` 在 `baseline_deny` 里 ⇒ **子代（含所有域会话）都看不到它**
⇒ 域会话无法自查工具面（v0.15.0 验证 illus-deep 时就是靠子代理**口头自报**
工具清单，才确认 67 件 illustrator 恢复可见）。

**实施**（用户裁决 2026-11-14 22:5x 采纳方案 A）：生产 `baseline_deny` 删掉
`explain_gate` 一项 ⇒ **71 → 70 件**。

| | 原状态 | 实施后 |
|---|---|---|
| 主会话 | 可用 | 可用（不变；`explain_gate` 从不在 `main_deny` 里） |
| 域会话（word-deep 等） | **不可见** | **可见** ⇒ 子代理能自查「我有多少工具、少了哪些、为什么少」 |
| 工具面税 | 0（它本来就被裁） | +1 件（每个域会话多一个只读诊断工具） |
| 安全影响 | 无 | **无** —— 它是只读的：不能改 config、不能改 lock、不能改任何 agent 的工具面 |
| 对 baseline 底线闸的意义 | 它不属于「高危执行类」 | 已归位 —— 底线闸的定位是**拦住能动手的工具**，诊断工具不在此列 |

**实测证据**（v0.15.2 上线后）：

- `preset_dispatch(word-deep)` 内 `explain_gate` **可见且调用成功**；
- 域会话面 **176 → 177**（自报 `可见 177/238 | 裁 61 件`）；
- canary 退出码 0：C4 逐组比对 `word-deep` 174 → 177（🟢 变大）/ 缩面 **0 组**；
- 改动最小侵入：与备份逐行 diff **只有 1 行差异**，其余 887 行逐字节未动。

**为何选方案 A 而不是 B**（B = 在各域 preset 的 `preset_allow` 里逐档加回）：

- A = 改**规则**（分类修正）；B = 加**例外**（`preset_allow` 里每一项都是
  「我特批这一件豁免」的例外清单）⇒ 例外清单天生比规则脆弱，且需逐档维护、漏了无提示；
- A 覆盖**所有**子代（含未来新装的 preset）；B 只覆盖显式加过的那几档；
- ★ A 之后仍可用 B 做**单点收紧**（某 preset 确需压到最小面时单独关掉）⇒ 不是二选一。

**生效机制（实测）**：`readConfig` **现读无缓存** + 裁剪发生在 `agent/created`
⇒ 改 config 对**之后创建的 agent** 立即生效，**无需重启**（host 代码改动才需重启）。

**边界**：`dispatch_composed` 的动态组装子代走 keep-only 精确 allow 名单，
`explain_gate` 不在任何能力标签名单里 ⇒ 那类子代仍不可见
（**非缺陷**，是「精确指定的面」的固有语义）。

**配套：岗位引导**（`agents-briefs/_common.md` 增「缺工具先自查」条）——
原先域子代只能报告「面内无此工具」，报告不出「被谁裁的」⇒ 缺了归因，主会话无法定位。
现引导：先调 `explain_gate` 看缺了什么、被哪条规则裁的，并给出 reason ↔ 修订动作对应；
`explain_gate` 只读，**修订一律由主会话在面板执行**。

**配套：输出完整性修复**（v0.15.2，★ 由域子代理实测发现）——
旧 render 只展开前 **20** 条明细却报全量件数 ⇒ 域会话看到「裁 61 件」只有 20 条
⇒ **看不到全貌**，违反铁律「报 N 件必须列 M 条(M<N) 且不声明」。
现两层输出：**按归因分组的完整汇总**（件数永不截断）+ 逐件明细上限 200 且显式声明未展开数。
实测：61 件 ⇒ 汇总 1 档 61 件、明细 61 条，**三者一致**（177 + 61 = 238 自洽）。
